01 Ploidy-cap resolution block

The single densest block in the whole app: a bash↔Python round trip that must survive being embedded inside an eval. Five things could each independently go wrong here, so every line earns its place.

code.sh : 96–115 Resolve ploidy-cap mode, decode the result back into bash 
EVAL=$(max_ploidy="${max_ploidy:-}" \       # ①
       ploidy_cap_purity_threshold="${ploidy_cap_purity_threshold:-}" \
       ploidy_cap_value="${ploidy_cap_value:-2}" \
       python3 - "$ATLAS" <<'PY'                         # ②
import sys, os, json
sys.path.insert(0, sys.argv[1])
from ploidy_gate import decide
d = decide(                                              # ③
    max_ploidy=(int(os.environ["max_ploidy"]) if os.environ.get("max_ploidy") else None),
    threshold=(float(os.environ["ploidy_cap_purity_threshold"]) if os.environ.get("ploidy_cap_purity_threshold") else None),
    cap_value=int(os.environ.get("ploidy_cap_value", "2")),
)
print("FIRST_ARGS_JSON=" + json.dumps(json.dumps(d.first_pass_args)))  # ④
print("CONDITIONAL=" + ("yes" if d.conditional else "no"))
print("MODE=" + d.mode.value)
PY
)
eval "$EVAL"                                              # ⑤
mapfile -t FIRST_ARGS < <(jq -r '.[]' <<<"$FIRST_ARGS_JSON")      # ⑥
①
Environment-scoped variable assignment. Placing VAR=value before a command sets it as an environment variable for that one command only — it does not leak into the rest of the script. This is the only way to hand a bash variable to a subprocess that doesn't otherwise share bash's variable namespace. ${max_ploidy:-} defaults to empty string if unset (required because set -u is active and this job input is optional).
②
Quoted heredoc delimiter. <<'PY' (quotes around PY) disables bash variable/command substitution inside the heredoc body — without the quotes, bash would try to expand $sys-looking tokens in the Python source itself, corrupting it.
③
The actual decision. This is the one line that calls the pure function covered in Part 3/§08. Everything else in this block is plumbing to get its inputs in and its output out.
④
Double JSON encoding — the trickiest line. d.first_pass_args is a Python list, e.g. ["-max_ploidy", "3"]. json.dumps(...) once turns that into the JSON text ["-max_ploidy", "3"]. Wrapping it in json.dumps(...) again turns that text into a JSON string literal — "[\"-max_ploidy\", \"3\"]" — with the inner quotes escaped. Printed after FIRST_ARGS_JSON=, this becomes a line that eval can safely treat as FIRST_ARGS_JSON='[\"-max_ploidy\", \"3\"]': a single-quoted assignment with no unescaped special characters, regardless of what the array actually contains. Skipping the second encoding would break as soon as an argument contained a double quote or a bash-special character.
⑤
The eval. This executes the three NAME=value lines Python printed, as if they'd been typed directly into the script — setting FIRST_ARGS_JSON, CONDITIONAL and MODE in the current shell. This is safe here specifically because the text being eval'd was generated by trusted first-party code moments earlier, not user input.
⑥
Decoding the (singly) JSON-encoded array. $FIRST_ARGS_JSON now holds the plain JSON array text (the double-encoding was only needed to survive the eval in step ⑤ — once decoded, it's back to ["-max_ploidy", "3"]). jq -r '.[]' prints each array element on its own line, unquoted; mapfile -t reads those lines into a real bash array, one element per line, with the trailing newline stripped from each (-t). The result, FIRST_ARGS, can now be safely expanded as "${FIRST_ARGS[@]}" even if an element contained spaces.

02 Conditional re-run gate

code.sh : 128–136 Decide whether pass 2 is needed, using the pass-1 result 
if [ "$CONDITIONAL" = "yes" ]; then                                          # ①
    PURITY=$(python3 -c "import sys;sys.path.insert(0,'$ATLAS');from purity import read_purity_ploidy as r;print(r('$PTSV').purity)")  # ②
    NEED=$(python3 -c "print('yes' if float('$PURITY') < float('${ploidy_cap_purity_threshold:-}') else 'no')")  # ③
    if [ "$NEED" = "yes" ]; then
        rm -rf "${WORK}"; mkdir -p "${WORK}"                                # ④
        run_purple -max_ploidy "${ploidy_cap_value:-2}"                        # ⑤
        [[ -s "${PTSV}" ]] || { echo "ERROR: … after pass 2"; exit 1; }
    fi
fi
①
Gate on mode, not on presence of a threshold. CONDITIONAL was set by decide() in the previous block — it's "yes" only in CONDITIONAL mode. This is deliberately checked instead of re-testing [ -n "$ploidy_cap_purity_threshold" ], because the mode decision (with its mutual-exclusion validation) already happened once in Python and should not be re-derived here.
②
One-off Python invocation via -c, not a heredoc. This needs only a single value back (.purity), so a one-liner is used instead of the heavier JSON-bridge pattern from Block 1 — appropriate because there's no list/array to transport and no risk of the value containing shell metacharacters (it's a float parsed from PURPLE's own output).
③
String interpolation of a float into a Python literal. float('$PURITY') — $PURITY is substituted by bash before Python ever sees the line, so Python receives e.g. float('0.79'). This works because $PURITY is bash's own captured output from the line above and is guaranteed to be a plain decimal string, not attacker-controlled text.
④
The idempotency guarantee, again. Identical to the pre-pass-1 clear in Phase 4 — see Part 2 §5. Skipping this line would leave pass-1's files sitting alongside pass-2's, and PURPLE's own overwrite behaviour for pre-existing files is not something this script relies on.
⑤
Only the cap flag differs. Everything else run_purple needs (AMBER_DIR, COBALT_DIR, SOMATIC_ARG, …) is still in scope from Phase 1–2 and doesn't need to be re-supplied — this is the payoff of factoring the PURPLE invocation into a closure in Part 3 §05.

03 Scalar-JSON extraction (the eval-free version)

code.sh : 143–152 Parse the final purity.tsv and get purity/ploidy/sex into bash scalars — without eval 
SCALARS_JSON=$(python3 - "$ATLAS" "$PTSV" <<'PY'
import sys, json
sys.path.insert(0, sys.argv[1])
from purity import read_purity_ploidy
f = read_purity_ploidy(sys.argv[2])                                     # ①
sex = f.sample_sex if f.sample_sex in ("male", "female") else "unknown"       # ②
print(json.dumps({"purity": f.purity, "ploidy": f.ploidy_int(), "sex": sex}))   # ③
PY
)
FPUR=$(jq -r '.purity' <<<"$SCALARS_JSON")                            # ④
FPLO=$(jq -r '.ploidy' <<<"$SCALARS_JSON")
FSEX=$(jq -r '.sex'    <<<"$SCALARS_JSON")
①
The single parse point. Whichever pass ran last, $PTSV (fixed earlier, unchanged by which pass produced it) points at the correct final result. read_purity_ploidy raises PurityParseError on malformed data, which propagates as a Python traceback and non-zero exit, tripping set -e.
②
Allow-listing the sex value. f.sample_sex came from PURPLE's TSV via purity.py (lower-cased there). This line only trusts it if it's exactly "male" or "female"; anything else — an unexpected value, a typo in PURPLE's output format in a future version — becomes "unknown" rather than being passed through unchecked. This is a deliberate hardening added after an earlier version of this script used eval on this value directly (see the callout below).
③
One JSON object, three fields, one encoding layer. Unlike Block 1, this JSON is not double-encoded, because it is never going to be eval'd — it's only ever read field-by-field with jq. This is the safer of the two bridge patterns in this file and is preferred whenever the payload doesn't need to become bash variable assignments directly.
④
jq -r strips quotes. Without -r ("raw output"), jq '.purity' would print 0.79 with surrounding quotes if the value were a JSON string; here the values are JSON numbers/strings and -r ensures FPUR ends up as the bare text 0.79, not "0.79", ready to pass to dx-jobutil-add-output … --class=float.
Gotcha this design avoids

An earlier revision of this script extracted these three values with a single eval "$(python3 … print(f'FPUR={f.purity}; FPLO={f.ploidy_int()}; FSEX={f.sample_sex or "unknown"}') …)" — i.e. Python printed a bash assignment statement directly, and bash eval'd it. That is unsafe specifically for FSEX, because its value originates from an external file (PURPLE's TSV, ultimately derived from a BAM header or sample metadata) rather than from trusted first-party code. A crafted or corrupted gender field could inject arbitrary shell commands into the eval'd string. The current version never eval's data that came from outside the script.

04 decide()

ploidy_gate.py : 33–52 The pure decision function 
def decide(max_ploidy, threshold, cap_value=2) -> PloidyDecision:
    if max_ploidy is not None and threshold is not None:            # ①
        raise PloidyConfigError(
            "max_ploidy and ploidy_cap_purity_threshold are mutually exclusive"
        )
    if max_ploidy is not None:                                          # ②
        if max_ploidy < 1:
            raise PloidyConfigError("max_ploidy must be >= 1")
        return PloidyDecision(
            PloidyMode.STATIC, ["-max_ploidy", str(max_ploidy)], False, cap_value, None
        )
    if threshold is not None:                                            # ③
        if cap_value < 1:
            raise PloidyConfigError("ploidy_cap_value must be >= 1")
        if not (0.0 < float(threshold) <= 1.0):                          # ④
            raise PloidyConfigError("ploidy_cap_purity_threshold must be in (0, 1]")
        return PloidyDecision(
            PloidyMode.CONDITIONAL, [], True, cap_value, float(threshold)
        )
    return PloidyDecision(PloidyMode.NONE, [], False, cap_value, None)          # ⑤
①
Mutual exclusion checked first, unconditionally. This must run before any mode-specific validation, otherwise a caller supplying both an invalid max_ploidy and a threshold might see a confusing "max_ploidy must be >= 1" error when the real problem is that both were supplied at all.
②
STATIC branch — first_pass_args is populated immediately. Unlike CONDITIONAL mode, STATIC needs no second pass: the cap is applied on the very first PURPLE invocation, so first_pass_args already contains -max_ploidy N and conditional is False.
③
CONDITIONAL branch — first_pass_args stays empty. Pass 1 must run unbounded so the app can observe PURPLE's natural fit before deciding whether to intervene; the cap only gets attached on a possible pass 2, via rerun_args() (Part 3 §09), not here.
④
Range check reads oddly on purpose. 0.0 < float(threshold) <= 1.0 is an open-closed interval: 0 itself is rejected (a threshold of zero can never trigger — see Part 3 §08's callout) but 1.0 is allowed (a threshold of 1 means "always re-run unless purity is exactly 1", a valid if extreme configuration).
⑤
The implicit default: no cap at all. If neither input was supplied, the function falls through all three ifs to this final line — PloidyMode.NONE, empty args, not conditional. This is the same code path a completely unconfigured workflow run takes, and it deliberately does not raise — a missing ploidy-cap configuration is a valid, common case, not an error.

05 read_purity_ploidy()

purity.py : 21–34 Parse PURPLE's purity TSV, guarding against malformed/non-finite data 
def read_purity_ploidy(path) -> PurityFit:
    with open(Path(path)) as fh:
        rows = list(csv.DictReader(fh, delimiter="\t"))                # ①
    if not rows:
        raise PurityParseError(f"no data rows in {path}")         # ②
    d = rows[0]
    try:
        purity = float(d["purity"])
        ploidy = float(d["ploidy"])
    except (KeyError, ValueError) as e:                          # ③
        raise PurityParseError(str(e)) from e
    if not math.isfinite(purity) or not math.isfinite(ploidy):     # ④
        raise PurityParseError(f"non-finite purity/ploidy in {path}")
    sex = d.get("gender", "").strip().lower()                     # ⑤
    return PurityFit(purity, ploidy, d.get("status", ""), sex)
①
DictReader over a tab-delimited file. PURPLE writes purity TSVs with a header row naming each column; csv.DictReader(..., delimiter="\t") turns each subsequent row into a dict keyed by those header names, so the code below can say d["purity"] instead of tracking a column index — robust to PURPLE adding new columns in a future version, as long as it doesn't rename existing ones.
②
Empty file is a distinct failure mode from bad data. Checked separately from the parsing try below because rows[0] would raise an unhelpful IndexError otherwise — this gives a clear "no data rows" message pointing at the actual file.
③
Two different exception types, one handler. KeyError means the column doesn't exist at all (PURPLE's output format changed unexpectedly); ValueError means the column exists but its text isn't a valid float (e.g. "NA"). Both are genuinely "the file is not in the expected shape" from this function's point of view, so they're caught together and re-raised as the same domain-specific error type — callers only need to catch PurityParseError, not know about csv/float internals.
④
The check this whole function exists to add. float("nan") and float("inf") both succeed as conversions — the try above would not catch either. This explicit second check is what turns "PURPLE technically wrote parseable-but-meaningless numbers" into a caught, named error instead of a silent bad value flowing all the way to a downstream workflow stage as a plausible-looking scalar.
⑤
Defaulting, then normalising. .get("gender", "") means a missing gender column doesn't raise (unlike purity/ploidy, sex is not considered essential enough to fail the whole parse over) — it becomes an empty string, then .strip().lower() normalises whatever text is present. The empty-string case is handled later in code.sh's own allow-list (Block 3, annotation ②), which maps anything that isn't exactly "male"/"female" to "unknown".
