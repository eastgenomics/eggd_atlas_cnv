eggd_cgp-purple — how the app works

A DNAnexus bash app that wraps PURPLE (purity/ploidy/copy-number fitting), adds an optional two-pass ploidy cap, and emits typed scalar outputs for the next workflow stage. Part 1 of 4: orientation before reading a single line.

01 What this file does

src/code.sh is the entry point of a DNAnexus app — a small, self-contained unit of compute that runs inside a cloud worker, downloads its declared inputs, does some work, and uploads its declared outputs. This particular app runs PURPLE (from the Hartwig Medical Foundation's hmftools suite), a Java tool that combines B-allele-frequency data (from AMBER), read-depth-ratio data (from COBALT) and an optional somatic VCF (from SAGE) to fit a sample's tumour purity (what fraction of cells are tumour) and ploidy (average copy number), then segments the genome into copy-number regions.

The app is not a thin wrapper. It adds a feature PURPLE itself does not have: an optional maximum-ploidy cap. Some low-purity samples get fitted to biologically implausible high ploidy values; the app can force a second, capped run when that happens. It also solves a wiring problem — a DNAnexus workflow cannot read a number out of a file to pass to the next stage — by parsing PURPLE's result file itself and re-emitting purity/ploidy/sex as first-class typed values the next stage can consume directly.

Not in scope

This file does not run AMBER, COBALT or SAGE (those are separate upstream apps in the same workflow), does not build the IGV report (a downstream app does that), and does not decide whether a ploidy cap should be applied from clinical judgement — it only executes whatever cap policy the workflow's inputs specify.

02 The 7 phases

The script's own comments number its phases [1/7] through [7/7]. Phase 3 is the interesting one — it delegates a decision to a bundled Python module rather than encoding the logic directly in bash, because the decision has enough edge cases (mutual exclusion, range validation) to deserve real unit tests.

03 Data flow

Inputs arrive as DNAnexus file references (opaque IDs); by the end they have become a mix of uploaded files and typed scalar values sitting in the job's output record.

Why this matters

The two JSON hand-offs (bash→Python→bash) exist because bash cannot safely represent a list of command-line arguments or a purity/ploidy/sex triple as plain text without risking word-splitting or injection bugs. JSON plus jq gives a delimiter-safe channel. Part 2 covers this pattern in depth.

06 Naming conventions

  • ALL_CAPS shell variables (WORK, PTSV, FPUR, SCALARS_JSON) are script-local state, distinct from DNAnexus job-input variables which arrive lower_snake_case (sample_id, amber_tar) because DNAnexus injects them as exact-cased bash variables matching the app's inputSpec names.
  • @dataclass(frozen=True) on both PloidyDecision and PurityFit signals "this is an immutable value object, not something you mutate after construction" — a deliberate defensive choice for values that flow between processes.
  • class PloidyMode(str, Enum) — inheriting from str as well as Enum means the enum members compare equal to plain strings and serialise cleanly to JSON without a custom encoder.
  • Trailing Error exception names (PloidyConfigError, PurityParseError) each subclass ValueError — they signal "the caller passed bad data", not a bug in this code.
  • Numbered comment banners (# ── 0. Sanitise … ──) mark phase boundaries inside main() and are the basis for the phase diagram in Figure 1.
