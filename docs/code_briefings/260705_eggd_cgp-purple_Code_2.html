01 Bash strict mode: set -euo pipefail

Concept: fail fast instead of silently continuing

By default, bash is extremely forgiving: a failed command doesn't stop the script, an unset variable silently expands to an empty string, and a failure in the middle of a pipe (a | b) is invisible if the last command in the pipe succeeds. set -euo pipefail turns all three behaviours off:

  • -e — exit immediately if any command returns non-zero
  • -u — treat referencing an unset variable as an error
  • -o pipefail — a pipeline's exit status is the last non-zero exit status of any command in it, not just the final one
# without pipefail, this "succeeds" even though grep found nothing to match:
false | true          # exit code 0 — the failure is hidden
# with pipefail:
set -o pipefail
false | true          # exit code 1 — the hidden failure surfaces
In this file: line 8, set -euo pipefail, applies for the entire script. This matters because the app has dozens of sequential steps (download, decompress, run PURPLE, parse, upload) where a silent partial failure would produce a subtly wrong result rather than an obvious crash — e.g. if bgzip -d -c ref.fasta.gz > ref.fasta failed partway through, without -e the script would carry on and run PURPLE against a truncated reference.

02 JSON as an IPC bridge (bash ↔ Python ↔ jq)

Concept: passing structured data between processes that don't share memory

Bash and Python are separate processes here — the script invokes python3 - with a heredoc, and the Python process's only way to communicate a result back is to print text to stdout, which bash then captures with $(...). That's fine for a single string, but this script needs to pass back a list of command-line arguments and, later, three differently-typed values (a float, an int, a string) in one round trip. Passing those as ad-hoc delimited text is fragile — what if a filename contains the delimiter? — so the script has Python print valid JSON, then decodes it in bash using jq, a JSON-aware command-line tool.

# Python side: print a JSON object as the sole line of stdout
print(json.dumps({"purity": 0.79, "ploidy": 2, "sex": "male"}))

# bash side: capture it, then pull out each field with jq
SCALARS_JSON=$(python3 script.py)
FPUR=$(jq -r '.purity' <<<"$SCALARS_JSON")   # -> 0.79
In this file: this pattern is used twice. First in Phase 3 (code.sh:96-115) to pass a PloidyDecision's argument list out of ploidy_gate.decide() — printed as FIRST_ARGS_JSON, a JSON-encoded array, itself wrapped in json.dumps(json.dumps(...)) (encode twice so the outer decode in bash yields a clean single-line string bash can safely eval as a variable assignment). Second in Phase 6 (code.sh:143-152) to pass PURPLE's parsed purity/ploidy/sex triple back — this later use deliberately avoids eval entirely and reads each field with jq -r instead, because the values there originate from an external file (PURPLE's TSV) and should never be interpreted as shell code.

03 Frozen dataclasses & str, Enum

Concept: immutable value objects that also behave like plain strings

@dataclass(frozen=True) auto-generates __init__, __repr__ and __eq__ for a class, and additionally makes every attribute read-only after construction — assigning to instance.field = x raises an error. This is a common pattern for "value objects": data that represents a fact (a parsed row, a decision) and should never be mutated once created, because sharing a mutable object between the parts of a pipeline that produced it and the parts that consume it is a classic source of bugs.

Separately, class PloidyMode(str, Enum) creates an enum whose members are also real strings. A plain Enum member does not equal the string with the same name (PloidyMode.STATIC != "static"); a str, Enum member does (PloidyMode.STATIC == "static" is True), and it serialises to JSON as a plain string without extra encoder configuration.

class PloidyMode(str, Enum):
    STATIC = "static"

print(PloidyMode.STATIC == "static")   # True — because it IS a str
print(json.dumps(PloidyMode.STATIC.value))  # "static" — clean JSON
In this file: ploidy_gate.py:9-11 defines PloidyMode this way so d.mode.value (used in code.sh:107, MODE=...) is a plain string ready to echo into the job log with no extra conversion. PloidyDecision and PurityFit are both frozen dataclasses (ploidy_gate.py:15, purity.py:11) — once decide() or read_purity_ploidy() returns one, nothing downstream can accidentally alter the parsed values.

04 DNAnexus scalar vs file outputs

Concept: not every app output is a file

A DNAnexus app declares typed outputs in its dxapp.json. Most outputs are file — the app uploads a file with dx upload and registers the resulting file ID with dx-jobutil-add-output name "$file_id" --class=file. But an app can also declare a float, int, string or boolean output — in that case, dx-jobutil-add-output takes the value itself, not a file ID, and the DNAnexus workflow engine can wire that scalar directly into another stage's input without either stage touching a file.

# file output: register an uploaded file's ID
dx-jobutil-add-output purple_tar "$(dx upload out.tar.gz --brief)" --class=file

# scalar output: register a value directly
dx-jobutil-add-output purity "0.79" --class=float
In this file: code.sh:174-176 registers purity, ploidy and sample_sex as scalar outputs. This is the entire reason purity.py exists — PURPLE itself only writes a TSV file; without this app parsing that file and re-emitting the three values as typed scalars, the next workflow stage (CNVkit calling) would have no way to receive PURPLE's purity/ploidy/sex except by also parsing the TSV itself, duplicating the parsing logic and its NaN/format edge cases in a second place.

05 The idempotent two-pass re-run pattern

Concept: a state machine with at most one retry, and a clean slate each time

PURPLE is deterministic given the same inputs and flags, so re-running it with a different flag (-max_ploidy) is safe as long as its previous output directory is fully cleared first — otherwise stale files from pass 1 could be mistaken for pass 2's output. The script enforces this with rm -rf "${WORK}"; mkdir -p "${WORK}" immediately before every invocation of run_purple, and the whole re-run is capped at one extra attempt by construction: the conditional branch that triggers pass 2 is not itself inside a loop.

In this file: code.sh:118-137. Note that only the PURPLE run itself is repeated — AMBER and COBALT (the upstream BAF/depth-ratio tools) are never re-run, because their outputs don't depend on the ploidy cap. Also note PTSV (the path to the purity TSV) is computed once, before either pass, and is valid after either pass because both write to the same WORK directory with the same filename — the variable doesn't need to be recomputed, only re-checked with [[ -s "${PTSV}" ]].
