01 main() — the whole script

code.sh defines exactly one top-level function, main(), plus one local closure (run_purple()) declared inside it. Everything below is a walk through main()'s body phase by phase, using the numbered comment banners already in the source as section boundaries.

Phase 0 — sanitise sample_id code.sh : 17–20
case "${sample_id}" in … lines 17–20 GUARD

Purpose: reject any sample_id that isn't a safe filename fragment, before it gets used to build paths and shell out to rm -rf.

Reads

  • $sample_id (job input)

Effect

  • Exits with status 1 and a message on stderr if unsafe; otherwise no-op

Key logic: a bash case pattern matches four unsafe shapes in one go — any character outside A-Za-z0-9._-, the empty string, a leading ., or a leading -. The leading-- check exists specifically because a value like -rf passed to a command expecting a filename could be misinterpreted as a flag.

Design decision

This guard is duplicated verbatim across five of the seven apps in the workflow rather than factored into a shared library, because each app is an independent DNAnexus deployable unit with no shared runtime — there is no "import the other app's code" mechanism, so small guards like this are copied rather than shared.

02 Phase 1 — download & validate the VCF pair

Download inputs, then validate somatic_vcf pairingcode.sh : 22–47
dx download ×8, then VCF pairing checklines 22–47PHASE 1

Purpose: pull every required file input to local disk, and enforce that the two optional somatic-VCF inputs are supplied together or not at all.

Downloads

  • purple_jar, amber_tar, cobalt_tar
  • gc_profile, target_regions_bed
  • ref_fasta (+ref_fai), ensembl_data
  • somatic_vcf + somatic_vcf_tbi (optional pair)

Produces

  • SOMATIC_ARG — either empty or "-somatic_vcf somatic.vcf.gz"

Key logic: the pairing check is a single compound boolean — (A set AND B unset) OR (A unset AND B set) — that is true exactly when the two inputs disagree about being present. This has to be checked before either is downloaded, otherwise a lone somatic_vcf with no index would download fine and only fail later, deep inside PURPLE's own error handling, with a much less clear message.

Why not just always require both?

somatic_vcf is genuinely optional at the workflow level — PURPLE can fit purity/ploidy from AMBER+COBALT alone, just less precisely. The pairing rule only says "if you're going to supply one, supply both", not "you must supply it".

03 Phase 2 — prepare inputs

Untar AMBER/COBALT, decompress FASTA, untar Ensembl datacode.sh : 49–68
tar -xzf ×3, bgzip -d, samtools faidxlines 49–68PHASE 2

Purpose: convert the downloaded archives into the directory layout and file formats PURPLE's command-line interface expects.

Reads

  • amber.tar.gz, cobalt.tar.gz, ensembl_data.tar.gz, ref.fasta.gz

Produces

  • AMBER_DIR, COBALT_DIR, ENSEMBL_DIR — directory paths
  • ref.fasta — plain-text FASTA + .fai index

Key logic: the directory names inside each tar are not known in advance (they're whatever the upstream AMBER/COBALT apps named them), so each is located by find . -maxdepth 2 -name "<marker-file>" -printf "%h\n" — search for a file that is known to exist only inside that directory, then print its parent (%h). Each lookup is immediately validated with [[ -n "${DIR}" ]] || { echo ERROR; exit 1; } so a malformed upstream tar fails here with a clear message rather than producing a confusing PURPLE crash later.

PURPLE requires a plain (non-bgzipped) FASTA, but the reference is stored bgzipped to save space — hence bgzip -d -c ref.fasta.gz > ref.fasta followed by re-indexing with samtools faidx (the downloaded ref_fai index applies to the compressed file, not the decompressed one, so it can't be reused).

04 Phase 3 — resolve the ploidy-cap decision

Call ploidy_gate.decide() via a Python heredoc, decode with jqcode.sh : 96–115
EVAL=$(… python3 - "$ATLAS" <<'PY' … )lines 96–115PHASE 3

Purpose: turn the three raw job inputs (max_ploidy, ploidy_cap_purity_threshold, ploidy_cap_value) into a concrete decision — which mode applies, and what extra CLI args (if any) pass-1 PURPLE should get.

Reads

  • the three job inputs, passed via environment variables into the subshell

Produces

  • FIRST_ARGS (bash array), CONDITIONAL, MODE

Key logic: the job inputs are bash variables, but the Python subprocess doesn't inherit bash variables automatically — only environment variables. So the invocation prefixes the python3 call with variable assignments (max_ploidy="${max_ploidy:-}" python3 - <<'PY' …), which sets them as environment variables for that one command only. Inside the heredoc, Python reads them back with os.environ.get(...), calls decide(), and prints three lines of KEY=value-shaped output, one of which is a JSON-encoded array wrapped in a second layer of JSON encoding (json.dumps(json.dumps(...))) so it survives being embedded inside an eval'd bash assignment as a single-quoted string with no unescaped special characters.

The result is captured into $EVAL and then literally executed with eval "$EVAL" — this is safe specifically because the three lines are fixed NAME=value assignments generated by trusted code (the heredoc), not arbitrary untrusted input. Finally mapfile -t FIRST_ARGS < <(jq -r '.[]' <<<"$FIRST_ARGS_JSON") decodes the JSON array into a real bash array, so it can later be safely expanded as "${FIRST_ARGS[@]}" without word-splitting problems.

Why not just eval the whole ploidy_gate.decide() call inline?

Because decide() can raise (PloidyConfigError) on invalid combinations, and a Python exception needs to become a non-zero bash exit code, not a value to parse. A heredoc that runs to completion and prints results is easier to reason about than mixing exception handling across a language boundary; if decide() raises, the Python process exits non-zero, $EVAL is never assigned, and set -e stops the whole script.

05 run_purple() — the PURPLE invocation closure

A local function capturing AMBER_DIR/COBALT_DIR/ENSEMBL_DIR/SOMATIC_ARGcode.sh : 76–90
run_purple() { … }lines 76–90HELPER

Purpose: avoid repeating PURPLE's ~10-argument command line twice (once per possible pass), while letting each call supply its own extra arguments.

Parameters

  • "$@" — extra PURPLE CLI args, e.g. -max_ploidy 2, or nothing

Side effect

  • Runs java -jar purple.jar, writing into ${WORK}/

Key logic: bash functions close over the enclosing scope's variables the same way nested Python functions do — run_purple refers to ${AMBER_DIR}, ${COBALT_DIR}, ${ENSEMBL_DIR} and ${SOMATIC_ARG} without receiving them as parameters, because they were already set by Phases 1–2 in the same main() invocation. Only the variable part of the command line — the ploidy-cap flags — is parameterised via "$@", because that's the only part that differs between pass 1 and pass 2.

06 Phases 4–5 — run pass 1, conditionally re-run

rm -rf/mkdir + run_purple, then optional second passcode.sh : 117–137
Pass 1 always; pass 2 iff conditional & purity below thresholdlines 117–137PHASE 4–5

Purpose: execute PURPLE at least once, and a second time with a ploidy cap if the first fit came back with implausibly low purity.

Reads

  • FIRST_ARGS, CONDITIONAL, ploidy_cap_purity_threshold, ploidy_cap_value

Produces

  • ${WORK}/${sample_id}.purple.purity.tsv and .range.tsv — guaranteed to exist afterward or the script has already exited

Key logic: after pass 1, the script re-invokes the same Python purity.read_purity_ploidy() helper used later in Phase 6, just to extract the single purity field — a small amount of duplicated parsing that's cheap and keeps the "did we cross the threshold" check colocated with the pass-1 verification, rather than restructuring the whole script around a shared parse-once step. If a second pass is needed, the WORK directory is wiped and recreated exactly as before pass 1 — see Part 2's discussion of the idempotent two-pass pattern for why this matters.

07 Phases 6–7 — parse final result, assemble & upload

Extract scalars via JSON+jq, bundle purple_tar, emit outputscode.sh : 139–182
SCALARS_JSON=$(…); FPUR/FPLO/FSEX via jq; tar; dx-jobutil-add-output ×7lines 139–182PHASE 6–7

Purpose: parse whichever pass's result is final, package everything for upload, and register the app's declared outputs.

Uploads

  • purple_tar, purity_tsv, purity_range_tsv
  • plots_tar (only if PNGs were generated)
  • cnv_somatic_tsv, cnv_gene_tsv (header-only fallback if PURPLE omitted them)

Scalar outputs

  • purity (float), ploidy (int), sample_sex (string)

Key logic: before tarring, the script cp -a "${WORK}/." "${AMBER_DIR}/" — copying PURPLE's output into the AMBER extraction directory — so that the final purple_tar bundles both PURPLE's own files and the AMBER B-allele-frequency file, because a downstream plotter app reads the AMBER BAF file out of purple_tar and this is the simplest way to guarantee it's present without changing the plotter's expectations.

The two CNV TSVs get a fallback: [ -f "${CNV_SOMATIC}" ] || printf '...' > "${CNV_SOMATIC}" writes a header-only file if PURPLE didn't produce one (this can happen on very low-signal samples) — guaranteeing the app always emits these two declared outputs, which matters because a DNAnexus app with a required output that's missing fails the whole job.

Design decision — why cp -a into AMBER_DIR rather than the reverse?

Copying PURPLE's (smaller) output into AMBER's (already-extracted) directory is cheaper than the other way round, and avoids re-tarring AMBER's contents from scratch. It also means AMBER_DIR ends up containing a superset that gets tarred once, rather than juggling two source directories at tar time.

08 decide() — ploidy_gate.py

decide(max_ploidy, threshold, cap_value=2)ploidy_gate.py : 33–52DECISION

Purpose: the single pure function that turns three raw config values into a validated PloidyDecision. Pure, meaning it has no side effects and always returns the same output for the same input — which is exactly why it's tested independently of the app that calls it.

Parameters

  • max_ploidy: int | None
  • threshold: float | None
  • cap_value: int = 2

Returns / raises

  • PloidyDecision on success
  • PloidyConfigError on invalid combinations

Key logic: the function is a cascade of early returns, in priority order:

  1. Both max_ploidy and threshold set → error (mutually exclusive modes).
  2. max_ploidy set alone → STATIC mode: validate it's ≥1, return a decision whose first_pass_args already contains ["-max_ploidy", "3"] (say) and conditional=False.
  3. threshold set alone → CONDITIONAL mode: validate cap_value ≥1 and threshold is in the open-closed range (0, 1], return a decision with empty first_pass_args (pass 1 runs unbounded) and conditional=True.
  4. Neither set → NONE mode: no cap at all, PURPLE's own defaults apply.
Why (0, 1] and not [0, 1]?

A purity threshold of exactly 0 would mean "the cap never triggers, because purity is never strictly less than 0" — a degenerate, meaningless setting the validation chooses to reject outright rather than silently accept as a no-op.

09 PloidyDecision.needs_rerun() / .rerun_args()

needs_rerun(fitted_purity) / rerun_args()ploidy_gate.py : 22–30DECISION

Purpose: two tiny methods that answer "should pass 2 happen?" and "what flags does pass 2 need?" given the decision already made by decide() and a purity value only known after pass 1 completes.

needs_rerun

  • param: fitted_purity: float
  • returns: bool

rerun_args

  • no params
  • returns: ["-max_ploidy", str(cap_value)]

Key logic: needs_rerun is a three-way and: the mode must be conditional, the threshold must not be None (a defensive check — it always is set when conditional=True, by construction in decide()), and the fitted purity must be strictly below the threshold. Note that the actual app script (code.sh) doesn't call this method at all — it re-implements the same comparison inline with a one-line python3 -c call (NEED=$(python3 -c "print('yes' if float('$PURITY') < float('...') else 'no')")). The method exists for callers of the Python API (and its own unit tests) and documents the intended contract, even though the bash caller takes a shorter path to the same comparison.

10 read_purity_ploidy() — purity.py

read_purity_ploidy(path) -> PurityFitpurity.py : 21–34PARSE

Purpose: the only place in the whole app that reads PURPLE's purity TSV, so every caller — the pass-1/pass-2 threshold check and the final scalar emission — gets identical parsing and identical error handling.

Parameters

  • path — path to *.purple.purity.tsv

Returns / raises

  • PurityFit(purity, ploidy, status, sample_sex)
  • PurityParseError on empty file, missing columns, or non-finite values

Key logic: reads the TSV with csv.DictReader (tab-delimited), takes only the first data row (PURPLE's purity TSV has exactly one), and converts purity and ploidy to floats inside a try/except that catches both a missing column (KeyError) and an unparseable value (ValueError), re-raising both uniformly as PurityParseError. It then explicitly checks math.isfinite() on both values — Python's float("nan") and float("inf") both parse successfully as floats but are not usable results, so this guard exists specifically to catch a PURPLE run that produced structurally valid but numerically meaningless output.

sample_sex comes from the TSV's gender column, lower-cased — PURPLE writes MALE/FEMALE, but the app's declared scalar output and the downstream stage that consumes it both expect lower case.
