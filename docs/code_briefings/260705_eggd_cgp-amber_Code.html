eggd_cgp-amber — how the app works

A DNAnexus bash app that runs AMBER to measure B-allele frequency at germline heterozygous sites, one of three parallel inputs PURPLE fits purity/ploidy from. This is a condensed, single-file explainer — the app is 59 lines with one linear flow.

Author Joo Wook Ahn Date 5 July 2026

01 What this app does

src/code.sh is the entry point of a DNAnexus app that wraps AMBER (Hartwig Medical Foundation's B-allele-frequency caller). Given a tumour BAM and a list of known germline heterozygous sites, AMBER measures — at each site — what fraction of reads carry each allele. Regions of the genome that have gained or lost copies show a skew away from the expected 50/50 split; PURPLE (a downstream app in the same workflow) uses this skew, together with read-depth data from COBALT, to fit a genome-wide copy-number profile.

This app is a straight conversion of a pre-existing DNAnexus applet into a versioned, namespaced app — the AMBER invocation itself, its flags, and its output name are all frozen exactly as they were, because a workflow already links to this app by that exact output name.

04 Key concept: the DNAnexus bash-app shape

Every app in this workflow — this one included — follows the same skeleton: a main() function that (1) downloads its declared inputs with dx download, (2) runs a tool, (3) checks the tool actually produced what's expected, and (4) uploads results with dx upload then registers them with dx-jobutil-add-output. The job's input variables (tumour_bam, sample_id, …) are injected as bash variables automatically by the platform — there's no argument parsing to write.

# the shape every app in this series shares:
set -euo pipefail
main() {
    # 1. validate/download inputs (dx download "$var" -o local_name)
    # 2. run the tool
    # 3. verify its output files exist and are non-empty
    # 4. dx upload + dx-jobutil-add-output
}
Why explicit output verification?

Java tools like AMBER can exit with status 0 even when a downstream step (like writing the .pcf piecewise-constant-fit file) silently failed. Checking [[ -s "$FILE" ]] — file exists and is non-empty — before uploading catches that class of "successful-looking failure" early, with a clear message, instead of letting a truncated or missing file propagate into PURPLE.

Verify outputslines 37–44VERIFY

Purpose: confirm AMBER actually produced usable output before spending time tarring and uploading it.

Key logic: two files are checked — the BAF TSV (the main result) and the PCF file (a Java-side piecewise-constant-fit summary). The comment (Java PCF failed?) flags that this second check exists specifically because that step has been observed to fail independently of the main BAF computation.

Tar & uploadlines 46–53UPLOAD

Purpose: package the whole AMBER output directory as one file and register it as the app's declared output.

Key logic: --no-same-owner on tar avoids trying to preserve the original file ownership when the tar is later extracted — irrelevant inside a container, but prevents a harmless warning. The two-step dx upload … --brief then dx-jobutil-add-output amber_tar "$id" --class=file is the standard file-output registration pattern used by every app in this workflow.

06 Line-by-line: the sample_id guard

The one piece of logic in this file dense enough to deserve line-by-line treatment.

code.sh : 9–12 Reject an unsafe sample_id before it's used as a path/tar-name component 
case "${sample_id}" in
    *[!A-Za-z0-9._-]* | "" | .* | -* )                          # ①
        echo "ERROR: unsafe sample_id '${sample_id}' …" >&2; exit 1 ;;  # ②
esac
①
Four unsafe shapes in one pattern, separated by |. *[!A-Za-z0-9._-]* matches any string containing a character outside the safe set (the ! inside the bracket negates it). "" matches empty. .* matches a leading dot (hidden-file-like names, and ./.. themselves). -* matches a leading hyphen — specifically because a value like -rf could be misread as a command flag by something downstream, even though nothing in this particular script passes sample_id to rm.
②
Error to stderr, non-zero exit. >&2 sends the message to stderr (where DNAnexus job logs expect error text), and exit 1 combined with set -e (in effect from line 5) stops the script immediately — no further phase runs.
Why this guard is duplicated, not shared

The identical four lines appear in five of the seven apps that make up this workflow. Each DNAnexus app is an independently deployable unit with its own bundled files and no shared runtime to import from — so small, stable guards like this are copied rather than centralised in a library.
